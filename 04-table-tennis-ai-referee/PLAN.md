# 탁구 AI 심판 시연 기획서

2026년 11월 9일 · v0.5

휴대폰 한 대로 탁구 단식을 촬영한다. 노트북의 판정 모델이 공의 궤적을 읽고 득점자를 정하면, 앱이 해당 랠리의 결과를 전광판에 한 번 반영한다. 첫 시연은 실내 탁구대 한 곳에서 **명확한 아웃과 상대 코트의 두 번째 바운드**를 자동 채점한다. 서브 렛도 학습하고, 자동 처리 여부는 검증 결과로 결정한다.

## 1 시연 범위와 진행 방식

- **환경**은 고정된 탁구대 1개, 선수 2명, 공 1개다. 한 게임 동안 선수 위치를 고정하고 첫 서브와 선수 A/B의 위치는 시작할 때 지정한다. 선수는 정해진 순서대로 서브하고, 랠리 사이에 공을 주울 때는 다음 서브까지 잠시 간격을 둔다.
- **시연 장면**은 A와 B가 각각 점수를 얻도록 번갈아 구성한다. 정상 서브와 여러 번의 리턴을 거친 뒤 아웃과 두 번 바운드를 각각 보여준다. 공을 줍는 장면과 공이 몸에 가려지는 장면도 넣어 오채점 여부를 보여준다.
- **전광판**에는 A/B 점수, 다음 서브, 직전 판정 결과, 확인 필요 또는 연결 끊김 상태를 표시한다. 진행자는 보류 건에 `A 득점`, `B 득점`, `다시 서브`를 입력하거나 직전 판정을 취소할 수 있다.
- **게임 규칙**은 11점 선승, 10대10 이후 2점 차 승리다. 서브는 2점마다 바꾸고, 10대10부터 매 점마다 바꾼다. 렛으로 다시 서브하면 점수와 서브 순서를 유지한다. 서브 동작 위반, 엣지와 옆면 구분은 진행자가 판단한다. [ITTF 탁구 경기 규칙 제2장](https://db.ittf.com/sites/default/files/public/2026-02/2026_Statutes_v1_consolidated_tc.pdf)

## 2 판정 기준

이 표는 촬영 영상을 라벨링하고 모델의 오판을 검토할 때 사용한다. 득점자는 학습한 모델의 출력으로 정한다.

| 장면 | 정답을 붙이는 기준 | 화면 동작 |
| --- | --- | --- |
| 명확한 아웃 | 정상 리턴 구간에서 마지막 타구 선수를 확인했고, 공이 상대 코트에 닿지 않은 채 상대 엔드라인 밖으로 나가는 궤적을 충분히 관측했다. | 마지막 타구의 상대에게 1점 |
| 두 번 바운드 | 유효한 서브 또는 리턴이 상대 코트에 처음 닿았고, 상대가 치기 전에 같은 코트에서 두 번째 바운드가 확인됐다. | 마지막 타구 선수에게 1점 |
| 서브 렛 | 서브가 네트에 닿았고 그 외에는 정상 서브였음을 확인했다. | 자동 처리 기준을 통과한 모델은 `다시 서브` 표시. 그 외에는 확인 요청 |
| 근거 부족 | 핵심 구간에서 공이 가려졌거나 화면 밖으로 사라졌거나, 엣지나 네트 접촉 여부를 구분하기 어렵다. | 점수 유지 후 확인 요청 |
| 아직 득점 없음 | 랠리가 이어지고 있거나, 랠리 사이에 공을 줍고 있다. | 점수 유지 |

앱은 랠리마다 ID를 부여하고 `서브 대기 → 랠리 진행 → 득점 확정·렛·확인 필요 → 서브 대기` 순서로 처리한다. 모델이 `아직 득점 없음`을 내면 계속 관찰한다. 같은 랠리 ID의 종료 결과는 한 번만 처리하고, 이미 닫힌 랠리의 늦은 응답은 무시한다. 판정을 취소하면 직전 점수와 서브 순서를 함께 복원한다.

2. **기준 모델 학습.** 경량 YOLO 계열 사전 학습 모델을 공 검출에 맞춰 미세 조정한다. 전체 프레임으로 기준을 만들고, 입력 축소로 공이 너무 작아지면 탁구대와 양쪽 타구·아웃 구간을 포함한 관심 영역을 비교한다. 공이 없는 프레임과 조명 반사도 넣어 오탐을 확인한다.
3. **휴대폰 영상으로 보완.** 학습용 세션에서 흐릿한 공, 가려지기 직전 공, 먼 쪽 코트의 작은 공을 골라 추가 라벨링한다. 검출 결과를 연속 프레임에서 연결해 촬영 시각, 공 중심 좌표, 검출 신뢰도, 누락 여부를 저장한다. 바운드 전후의 검출 누락과 오탐을 별도로 기록한다.

## 4 득점 판정 모델 학습

공의 궤적을 입력받는 **작은 GRU 분류기**를 초기 가중치부터 직접 훈련한다. VideoJev에서 가져올 설계는 모델이 정해진 답 후보에 점수를 매기고 판정 하나를 고르는 방식이다. 이 프로젝트에서는 입력을 공 궤적으로, 출력은 `A 득점`, `B 득점`, `아직 득점 없음`, `보류`, `렛`으로 고정한다. [VideoJev 논문](https://arxiv.org/abs/2610.18615) · [PyTorch GRU](https://docs.pytorch.org/docs/main/generated/torch.nn.GRU.html)

### 촬영과 라벨링

탁구대와 상대 선수를 확보한 상태에서 최소 두 번의 촬영 세션으로 **첫 개발 데이터 80~120개**를 모은다. 아래 수량은 첫 학습과 오판 분석을 위한 목표다. 한 랠리에서 여러 구간을 잘라도 촬영량은 원본 장면 기준으로 센다. 촬영 전에는 참가자에게 영상 저장과 사용 범위를 안내한다.

| 정답 | 첫 수집 목표 | 포함할 장면 |
| --- | --- | --- |
| `A 득점` | 20~30개 | B의 아웃과 B 코트의 두 번 바운드를 고르게 포함 |
| `B 득점` | 20~30개 | A의 아웃과 A 코트의 두 번 바운드를 고르게 포함 |
| `아직 득점 없음` | 15~20개 | 정상 서브, 랠리 도중, 두 번째 바운드 직전 리턴, 공 줍기 |
| `보류` | 10~15개 | 핵심 순간 가림, 프레임 누락, 엣지 의심, 판정이 불명확한 서브 |
| `렛` | 15~25개 | 양쪽 선수의 정상적인 네트 접촉 서브. 접촉 여부가 확실한 사례를 사용 |

촬영 세션 ID, 랠리 ID, A/B 위치, 서브 선수, 판정 가능해진 시각과 정답을 기록한다. 득점으로 끝난 랠리도 **득점 전에 잘린 구간**은 `아직 득점 없음`으로 표시한다. 영상이 애매한 경우에는 `보류`를 붙인다. 렛과 비슷해 보이는 정상 서브도 함께 촬영한다. 태그는 모델에 정답을 알려주거나 오판 원인을 분석하는 데 쓴다. 모델 입력에는 해당 시점까지의 궤적만 사용한다.

### 훈련과 모델 선택

1. **먼저 데이터 분리.** 촬영 세션 단위로 학습과 검증을 나눈다. 같은 랠리에서 나온 연속 프레임과 겹치는 구간은 같은 묶음에 둔다. 검증 세션은 공 검출기 보완 학습에도 쓰지 않는다. 최종 시연 평가는 모델과 기준을 정한 뒤 별도 세션에서 진행한다.
2. **입력 만들기.** A/B 방향을 고정하고, 화면 크기와 탁구대 기준으로 좌표를 정규화한다. 프레임 간 시간차, 공 좌표, 검출 신뢰도와 누락 표시를 함께 넣는다. 가려진 프레임은 누락 표시를 남긴다. 첫 실험은 현재 시각까지 최근 약 2초를 사용하고, 검증 영상에서 서브나 마지막 타구가 잘리면 구간 길이를 조정한다.
3. **처음부터 학습.** PyTorch에서 GRU 1층과 다섯 가지 선택지의 점수를 내는 출력층으로 시작한다. 작은 배치 하나에서 학습 손실이 내려가는지 먼저 확인한 뒤 전체 학습 세트에 교차 엔트로피 손실을 적용한다. 검증 결과와 함께 모델 가중치, 학습 설정, 세션 분리 목록을 저장한다. [PyTorch 교차 엔트로피 손실](https://docs.pytorch.org/docs/stable/generated/torch.nn.CrossEntropyLoss.html)
4. **오판 분석.** 검증 영상에서 정상 서브를 렛으로 고르는 경우, 랠리 도중 점수가 올라가는 경우, A/B를 뒤바꾸는 경우를 따로 센다. 자동 처리와 보류를 나누는 기준은 검증 영상에서 정한다. 궤적만으로 렛과 정상 서브를 안정적으로 구분하지 못하면, 렛 후보는 확인 대상으로 표시한다. 진행자가 렛을 확인하면 같은 서버가 다시 서브한다.

**학습 장비.** Windows 노트북의 RTX 5050 Laptop GPU 8GB와 RAM 16GB를 사용한다. Blackwell을 지원하는 Windows용 PyTorch CUDA 빌드를 설치하고, 실제 GPU에서 작은 배치로 역전파까지 실행해 확인한다. 공 검출기는 작은 모델과 배치로 시작해 메모리 사용량을 보고 조정한다. [NVIDIA 노트북 GPU 사양](https://www.nvidia.com/en-us/geforce/laptops/compare/) · [PyTorch 설치 안내](https://pytorch.org/get-started/locally/)

## 5 휴대폰 전송과 PC 판정 구조

휴대폰은 실시간 영상만 보낸다. **영상 디코딩, 공 검출과 추적, 득점 판정, 점수판은 모두 Windows 노트북에서 실행한다.** 학습이 끝난 공 검출기와 GRU의 가중치는 시연 프로그램을 시작할 때 PC에서 불러온다.

```text
아이폰 후면 카메라 → Camo Camera 앱
  ↓ USB 데이터 케이블 또는 같은 Wi-Fi
Windows Camo Studio → 가상 웹캠 Camo Camera → OpenCV 프레임 수신
  ↓
YOLO 공 검출 → 공 추적 → GRU 판정 → 전광판
```

### 휴대폰과 Windows 연결 방식 비교

**1차 경로는 보유한 아이폰을 Camo로 USB 연결하는 방식**이다. USB 케이블을 두기 어려운 장소에서는 같은 Camo 앱으로 Wi‑Fi 연결을 시험한다. Camo Studio가 영상을 Windows에 가상 웹캠으로 내보내므로, 두 경로에서 Python 판정 프로그램은 같은 방식으로 카메라 프레임을 읽는다. iPhone의 연속성 카메라(Continuity Camera)는 Mac용이다. [Camo 연결 안내](https://camo.com/support/camo/camo-getting-started) · [Apple 연속성 카메라 안내](https://support.apple.com/en-ie/102546)

| --- | --- |
| 아이폰과 Camo USB | 기본 경로. USB 데이터 케이블과 Windows용 Camo Studio를 사용한다. 무료판은 720p·30fps를 지원하며, 더 높은 해상도와 최대 60fps 설정은 Pro 기능이다. 실제 수신 프레임률은 기기와 설정에 따라 측정한다. [Camo 기능 비교](https://camo.com/pricing) |

[DroidCam Windows 연결](https://droidcam.app/windows/) · [USB 안내](https://droidcam.app/help/#usb-setup) · [기능 비교](https://droidcam.app/pro-info.html) |

| Android USB 웹캠 | 앱 개발에 앞서 USB 영상 품질을 비교할 때 쓴다. 지원하는 기기에서는 USB 데이터 케이블로 연결하고 휴대폰의 USB 옵션에서 `웹캠`을 선택한다. [Google Pixel USB 웹캠 안내](https://support.google.com/pixelcamera/answer/14274129?hl=en) |

### 첫 연결 절차

1. **설치.** 아이폰에 App Store의 `Camo Camera`, 노트북에 `Camo Studio`를 설치한다. Windows에서 다른 앱이 Camo 영상을 읽을 수 있도록 초기 설정에서 호환성 추가 기능 설치 안내를 따른다. [Camo 다운로드](https://camo.com/downloads) · [Windows 설치 안내](https://camo.com/support/camo/camo-getting-started#installing-on-windows)
2. **USB 연결.** 아이폰과 노트북에서 앱을 실행한다. 아이폰 단자에 맞는 Lightning 또는 USB‑C 데이터 케이블로 연결하고 Camo Studio의 `Device`에서 아이폰을 선택해 후면 카메라 미리보기를 확인한다. 아이폰이 목록에 없으면 케이블이 데이터 전송을 지원하는지, Apple Mobile Device Services가 준비됐는지 확인한다. [Camo 아이폰 연결](https://camo.com/support/camo/camo-getting-started#using-camo-with-an-iphone) · [Camo 연결 문제 해결](https://camo.com/support/camo/troubleshooting-camo)
3. **Wi‑Fi 연결이 필요한 경우.** 두 기기를 같은 로컬 네트워크에 연결한다. Camo Studio의 `Device → + Pair Camo Camera`에서 QR 코드를 띄우고 아이폰 앱의 무선 연결 버튼으로 스캔한다. 아이폰이 로컬 네트워크 접근을 요청하면 허용한다. 기기가 같은 네트워크 이름을 써도 서로 연결되지 않는 장소라면 USB로 돌아간다. [Camo Wi‑Fi 연결 안내](https://camo.com/support/camo/camo-getting-started#using-camo-with-an-iphone) · [Camo 연결 문제 해결](https://camo.com/support/camo/troubleshooting-camo)
4. **Python 수신 확인.** Camo Studio를 실행한 채 OpenCV `VideoCapture`에서 `Camo Camera`에 해당하는 카메라 번호를 확인한다. 내장 카메라가 열리면 번호를 바꾸고, 기본 카메라 방식에서 장치를 열 수 없으면 Windows의 `CAP_DSHOW`와 `CAP_MSMF`를 각각 시험한다. Camo Studio에는 영상이 보이는데 Python에서 열리지 않으면 Windows의 데스크톱 앱 카메라 권한을 확인한다. 미리보기에 아이폰 앞에서 움직인 물체가 보이면 프레임 수신 경로가 연결된 것이다. [OpenCV 카메라 입력](https://docs.opencv.org/4.x/d8/dfe/classcv_1_1VideoCapture.html) · [Windows 카메라 권한](https://support.microsoft.com/en-us/windows/privacy/manage-app-permissions-for-a-camera-in-windows)

### 전송 품질 시험

- **첫 실험.** Camo 무료 설정인 720p·30fps에서 시작한다. 노트북에서 모델을 끄고 5분간 미리보기를 띄운 뒤, 같은 설정에서 모델을 켜고 다시 측정한다. 실제 받은 프레임 크기, 초당 수신·처리 프레임 수, 프레임 사이의 긴 공백과 눈에 띄는 멈춤을 기록한다. 카메라 설정에 30fps가 표시되는 것과 서로 다른 영상 프레임 30장이 매초 도착하는 것을 구분한다.
- **지연 측정.** 잠깐 아이폰으로 노트북 화면 한쪽의 스톱워치를 촬영한다. PC 화면에 원본 스톱워치와 수신 미리보기를 나란히 띄우고 같은 시점의 두 숫자 차이를 여러 번 기록한다. 이 값은 카메라부터 PC 미리보기까지의 대략적인 지연이다. 모델을 켠 뒤에는 기존 기준대로 랠리 종료부터 점수판이 바뀌는 시간도 별도로 잰다.
- **화질과 연결 방식 결정.** 같은 카메라 위치와 조명에서 아웃과 두 번 바운드를 각 5회 찍어, 먼 쪽 공의 크기와 타구·바운드 전후 프레임을 확인한다. 공이 작거나 접촉 순간이 빠지면 휴대폰 위치와 조명을 먼저 조정한 뒤, 사용할 수 있는 경우 1080p 또는 60fps를 각각 비교한다. USB와 Wi‑Fi 중 둘 다 시험했다면 이 장면들이 잘 보이고 지연·끊김이 적은 경로를 시연에 쓴다.
- **끊김과 복구.** 랠리 도중 케이블을 빼거나 연결을 끊어 점수가 올라가지 않는지 확인한다. 재연결 후 카메라가 정상 수신되는지, 앞 랠리의 판정이 새 랠리에 반영되지 않는지 확인한다.

### Android 송출 앱 직접 개발

Windows 노트북에서 **Android Studio와 Kotlin**으로 Android 송출 앱을 개발한다. 아이폰과 Camo는 PC 판정 프로그램을 먼저 연결해보는 데 쓴다. Android 개발 단계에서 USB는 앱 설치와 디버깅에 사용하고, 첫 영상 송출은 두 기기가 연결된 로컬 Wi‑Fi에서 검증한다. [Android Studio 설치](https://developer.android.com/studio/install) · [실기기 실행 안내](https://developer.android.com/studio/run/device)

**Android 후면 카메라 → Camera2 → H.264 인코딩 → SRT 송출 → Windows FFmpeg 수신 → 기존 판정 흐름**

1. **기기 확인.** Android를 확보하면 후면 카메라의 Camera2 출력 크기와 프레임 간격, H.264 인코더가 지원하는 해상도·FPS 조합을 확인한다. 기본 카메라 앱의 녹화 사양과 별도로 직접 만든 앱에서 실제 촬영·전송되는 FPS를 측정한다. [Camera2 출력 설정](https://developer.android.com/reference/android/hardware/camera2/params/StreamConfigurationMap) · [Android 인코더 지원 범위](https://developer.android.com/reference/android/media/MediaCodecInfo.VideoCapabilities)
2. **송출 기능 구현.** 앱에는 PC의 로컬 IP와 포트, 촬영 모드, 시작·중지, 연결 상태만 둔다. Camera2와 H.264·SRT를 지원하는 RootEncoder를 사용한다. 첫 목표는 **1080p·30fps로 수신을 확인한 뒤 1080p·60fps를 비교**하는 것이다. 첫 연결이 불안정하면 720p·30fps로 낮춰 연결부터 확인한다. [RootEncoder 공식 저장소](https://github.com/pedroSG94/RootEncoder)
3. **PC에서 수신 확인.** 예를 들어 PC 주소가 `192.168.0.20`이면 PC에서 SRT를 지원하는 `ffplay "srt://192.168.0.20:9000?mode=listener"`로 대기하고, Android에서 `srt://192.168.0.20:9000`으로 송출한다. 미리보기가 확인되면 `capture.py`의 SRT 입력을 FFmpeg로 연결해 디코딩한 프레임과 영상 시각을 기존 판정 흐름에 전달한다. [FFmpeg SRT 문서](https://ffmpeg.org/ffmpeg-protocols.html#srt)
4. **시연 모드 선택.** 같은 구도에서 30fps와 60fps를 각각 최소 5분 시험하고, Android 촬영 FPS, PC 수신 FPS, 공 추적 처리 FPS를 나눠 기록한다. 타구와 바운드가 더 잘 보이고 점수 표시 지연도 기준 안에 들어오는 모드를 채택한다. 추론이 밀리면 검출 입력에서 탁구대와 타구 공간을 포함하는 관심 영역을 먼저 시험하고, 조정 후에도 늦으면 30fps를 사용한다.

### 영상 연결과 판정 흐름

1. **촬영.** 휴대폰을 네트 옆의 비스듬한 각도에 고정해 탁구대 네 모서리, 양쪽 타구 공간과 엔드라인 뒤를 담는다. PC는 라이브에서 Camo 가상 웹캠 또는 Android SRT 스트림을 받고, 오프라인 평가에서는 녹화 파일을 읽는다.
2. **영상 수신과 공 추적.** 수신 단계에서 각 프레임에 순번과 시간 정보를 붙인다. 스트림이나 파일이 제공하는 영상 시각을 우선 쓰고, 라이브에서 이를 얻기 어려우면 PC의 단조 증가 수신 시각을 대용으로 쓴다. 트래커는 프레임의 순번과 시각을 공 좌표에도 그대로 붙인다. 추론이 밀리면 대기 프레임 수를 제한하고 버린 프레임을 기록한다. 수신 지연·프레임 누락과 화면에서 공을 못 찾은 경우를 구분한다.
3. **모델 판정.** 시작 때 화면에서 탁구대 네 모서리와 A/B 위치를 지정한다. 활성 랠리에서 최근 약 2초의 공 좌표, 프레임 간 시간차, 검출 신뢰도와 누락 표시를 학습 때와 같은 방식으로 전처리한다. GRU는 다섯 가지 결과의 점수를 반환한다. 앱은 검증에서 정한 점수와 연속 출력 기준을 만족할 때 종료 결과를 반영한다. 영상에 큰 공백이 생겼거나 결과가 확정되지 않은 채 플레이가 끝나면 진행자가 확인한다.
4. **점수판 갱신.** 모델이 `A 득점`을 확정하면 해당 랠리 ID로 A에게 1점을 반영한다. 같은 랠리의 중복 결과나 이미 종료된 랠리의 늦은 결과는 건너뛴다. `렛`은 점수와 서버를 유지하고, `아직 득점 없음`은 계속 관찰하며, `보류`는 확인 요청을 표시한다. 영상이 끊기면 현재 점수를 유지하고 진행 중이던 랠리를 확인 대상으로 둔다. 연결이 복구되면 진행자가 해당 건을 정리한 뒤 새 랠리로 시작한다.

첫 실시간 리허설에서는 진행자가 서브 전에 랠리 시작 버튼을 누른다. 실시간 득점 판정이 안정되면 서브 시작 자동 감지를 붙여 버튼 없이 같은 흐름을 검증한다. 지연을 조사할 때는 PC 수신부터 화면 표시까지 걸린 시간과 랠리 종료부터 실제 점수 표시까지 걸린 시간을 구분한다.

### Python 코드 구성

| 파일 | 맡는 일 |
| --- | --- |
| `app.py` | PC 실행 진입점. 영상 소스와 가중치를 열고, 최근 궤적과 활성 랠리를 관리한다. 미리보기와 점수판, 시작·확인·취소 조작을 연결한다. |
| `capture.py` | Windows 카메라와 녹화 파일은 OpenCV로 읽는다. Android SRT 경로를 구현할 때는 FFmpeg로 디코딩한 프레임을 같은 형식으로 넘긴다. 세 입력에서 프레임 순번, 시간, 연결 상태를 제공한다. |
| `ball.py` | YOLO 검출과 프레임 간 공 추적을 수행한다. 공의 중심 좌표, 검출 신뢰도와 누락 여부를 반환한다. |
| `referee.py` | 궤적 전처리와 GRU 모델을 정의한다. 가중치를 불러와 `판정 종류, 판정 점수`를 반환한다. |
| `scoreboard.py` | 랠리 ID별 결과를 한 번 반영한다. 점수와 서브 순서, 게임 종료, 수동 확인과 취소 이력을 관리한다. |
| `train_detector.py` | Roboflow의 공 박스 데이터로 YOLO를 학습하고 검출기 가중치를 저장한다. |
| `train_referee.py` | 녹화 영상에 `ball.py`를 적용해 궤적을 만든 뒤, 판정 라벨로 `referee.py`의 GRU를 학습한다. 가중치와 입력 설정, 판정 종류의 순서를 함께 저장한다. |

녹화 재생과 라이브는 `capture.py`에 넘기는 입력만 바꾼다. 공 추적, 궤적 전처리, 판정과 점수 반영은 같은 코드를 사용한다. 연결 시험에서는 먼저 녹화 파일로 `7대5 → A 득점 → 8대5`를 확인한 뒤, 같은 결과를 반복 전송하거나 중간에 영상 연결을 끊어도 점수가 한 번만 반영되는지 검증한다.

## 6 검증 기준과 제작 순서

최종 테스트는 학습과 기준 조정에 쓰지 않은 촬영 세션에서 진행한다. **명확한 아웃 20개, 두 번 바운드 20개, 진행 중·비랠리 10개, 보류 10개, 서브 렛 10개**를 목표로 한다. 진행 중·비랠리에는 정상 서브 뒤 랠리가 이어지는 장면을 포함한다. 완성된 클립과 함께 서브부터 시간순으로 재생하는 방식도 평가해 득점 시점을 비교한다. 아래 수치는 시연 준비 여부를 판단하기 위한 제안값이다.

| 검증 항목 | 첫 시연 통과 기준 |
| --- | --- |
| 자동 채점 | 아웃과 두 번 바운드 각각 20건 중 18건 이상을 올바른 선수에게 자동 반영. 보류와 미감지도 분모에 포함 |
| 오채점과 중복 | 잘못된 선수 득점과 랠리당 중복 득점 0건. 진행 중·비랠리, 보류, 렛에서도 자동 가점 0건 |
| 자동 렛 | 정상 서브를 렛으로 처리한 건이 0건이고, 서브 렛 10건 중 8건 이상을 자동 처리할 때 시연에서 사용. 그 기준에 못 미치면 렛 후보를 진행자가 확인 |
| 실시간 지연 | 라이브에서 정상적으로 자동 채점된 랠리의 90%가 종료 후 1초 이내에 표시. 수신·처리 프레임률과 프레임 누락률도 함께 기록 |
| 점수 규칙 | 10대10 이후 서브 교대, 11대10에서 계속 진행, 12대10에서 종료, 렛과 취소 후 상태 복원, 연결 끊김 후 재시작 확인 |

| 순서 | 작업 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| 1 촬영 실험 | 아이폰을 Camo USB로 연결하고, 삼각대 각도를 잡아 아웃과 두 번 바운드를 각 5회 녹화 | Python이 아이폰 영상을 받고, 실제 수신 프레임률과 미리보기 지연을 기록할 수 있음 |
| 2 공 검출 | Roboflow로 기준 모델 학습 후 휴대폰 영상에 검출과 궤적을 표시 | 공이 끊기는 구간과 오탐 원인을 확인하고 부족한 장면을 추가 촬영 |
| 3 녹화 판정 | 다섯 가지 정답을 붙인 궤적으로 GRU를 학습하고 점수판에 연결 | 득점자 오류, 이른 득점, 렛과 보류를 구분해 검증하고 사용할 자동 처리 기준을 정함 |
